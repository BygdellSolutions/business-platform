# Local capacity test — 13 October 2026

The current deployment has an overload failure that must be fixed before relying on rapid growth to 1,000 users. The architecture can stay; adding workers alone is not a sufficient overload policy.

## Setup and scope

- Freshly built repository backend and frontend Docker images; default backend CMD has one Uvicorn worker.
- PostgreSQL 17 on the dedicated local test server, port 5433. Each run creates a separate guarded `capacity_<random>_test` database, migration owner and restricted runtime role. Existing development, staging and shared test schemas are untouched. Scratch services, databases and roles are removed afterwards.
- Initial fixture: 1,000 users, 20 organizations with 50 members each, 5,000 customers, 2,000 service catalog items, 5,000 completed orders and 15,000 order lines. Business phases create additional customers. Invoice lists are initially empty; orders are eligible for invoicing.
- Real session authentication and tenant membership resolution, plus normal BFF handling. Synthetic sessions are inserted for the fixture; password-login tests perform real Argon2 verification. Authentication and foreign-organization rejection are checked before the Linux phases.
- Production backend configuration and image. Frontend is the production **build**, with development runtime configuration only for localhost HTTP/cookies, as in the repository rehearsal. No TLS, Coolify proxy, external network or browser rendering costs are measured.
- Docker Desktop has 16 logical CPUs and about 15.6 GiB RAM available. Containers have no CPU or memory quota. PostgreSQL test storage is tmpfs. These numbers do **not** size a smaller production VPS.
- Independent Linux HTTP generator. Fifteen-second stages, with app-container restarts and readiness checks between stages to remove queued work from earlier overload. This is a capacity probe, not a prolonged soak or recovery test.

The mixed business workload cycles customer lists, catalog lists, order lists, invoice lists and customer creation (roughly 20% writes; page size 25). It does not exercise stock contention, invoice issuance, payment recording, uploads or email. The dashboard API workload measures `/api/invoices/summary`, including a 250-order eligible backlog per organization.

With 1,000 virtual users staggered over ten seconds, each attempting one API request every ten seconds (about 100 offered requests/s), **598 of 2,999 requests timed out: 19.9%**. Overall p95 was 17.7 seconds. This short scenario rotates through customer, catalog and order lists; it is not 1,000 complete page loads or a long-duration mixed workload.

The default pool has 15 possible connections per process (5 retained plus 10 overflow). During an overload stall, a read-only PostgreSQL diagnostic found **15 connections idle in transaction**, waiting on the client, while API CPU usage dropped near zero. Pool checkout timeouts were also observed. These observations are consistent with synchronous dependency scheduling exhausting threads while earlier requests hold their database sessions. They are not evidence that PostgreSQL ran out of compute capacity. The frontend's 15-second fetch timeout does not promptly clear this server backlog.

The measured ordinary-request throughput plateau is around 110–120 successful requests/s for this fixture. The tested burst failure boundary lies between 50 and 100 simultaneously active requests; this is **not** a limit of 50 registered or logged-in users. The dashboard's plateau is much lower and its implementation loads every eligible candidate and its lines before computing totals in Python.

## Experiments

The experiment wrapper in `backend/tools/admission_app.py` gates the **whole request before its synchronous dependencies execute**, with 12 running requests per worker, at most 48 waiting and a one-second admission timeout. Saturation returns 503 with Retry-After. It is mounted only into disposable test containers and is not part of the app or deployment. The wrapper's concurrency, queue timeout and exception cleanup were checked independently.

With one worker and this wrapper, the same paced 1,000-account scenario returned 2,918 successes and 81 busy responses (2.7%), with **no timeout responses** and p95 679 ms. This strongly supports request/pool starvation as the overload mechanism. Admission makes failure bounded; additional capacity is still needed to eliminate rejections at the target workload.

With four workers and admission:

| Workload | Offered load | Result | p95 |
|---|---|---|---:|
| Mixed business, 50 concurrent users | Sustained closed loop | 220.2 successful requests/s; 3,357 / 3,357 succeed | 479 ms |
| Paced 1,000-account API scenario | About 100 API requests/s | 2,999 / 2,999 succeed | 66 ms |
| Complete SSR dashboard, 10 concurrent users | Sustained closed loop | 309 / 309 succeed; 20.3 complete pages/s | 752 ms |
| Complete SSR dashboard, 1,000 paced users | One dashboard page/user/30 s, over 60 s | **675 / 2,000 complete successfully; 66.3% fail** | 3.26 s overall; 3.36 s for successful pages |

The complete dashboard renders the real Next.js page and layout, including their multiple authenticated API calls. A successful HTTP status alone is insufficient: 795 responses returned HTTP 200 with a streamed error instead of dashboard content; another 530 returned HTTP 500. The probe checks the dashboard's rendered marker to distinguish these from successful pages. JavaScript, assets and browser interaction are still outside this measurement.

The independent, CPU-only PDF benchmark rendered 10, 100, 500 and 2,000 simple lines three times each. Median times in the final run were 27 ms, 150 ms, 730 ms and **3.05 seconds**, respectively; the first render also includes font loading. The final run explicitly refuses any attempted database connection. This measures the renderer only, not invoice reads/storage or simultaneous downloads. Rich fields and long descriptions may cost more. Large PDFs meet the plan's threshold for background preparation.

During the paced dashboard phase, sampled backend CPU averaged about **4.6 logical cores**, frontend about **0.8 core**, and PostgreSQL about **0.9 core**. The generator used about 0.18 core. This phase was not limited by the generator. The guarded API rejected excess work, and a failure in a page's required parallel reads became a page error. The four-worker change therefore passes the simpler paced API scenario but **does not establish readiness for 1,000 actively navigating dashboard users**. Optimising summary work is necessary before claiming that capacity; a larger worker count alone needs a fresh connection/CPU budget and retest.

## Required changes before a 1,000-user growth target

1. Implement and review whole-request admission in the real backend, including cancellation, overload responses and metrics. Give pool checkout and queries explicit finite timeouts, and handle pool exhaustion with a safe 503 rather than an unhandled exception. Keep concurrent database-using requests within the pool budget so downstream synchronous dependencies can finish.
2. Add API replicas/workers with working routing; the current BFF points to a single fixed backend container. Budget total database connections across all API processes, queue workers, probes and operator jobs. Four processes with the current defaults can use 60 API connections. Add PgBouncer when the measured connection budget calls for it.
3. Tune Argon2 admission to the **total machine CPU/memory budget**. Four workers currently permit 16 concurrent hashes in total; multiplying processes is not permission to multiply hashing resource use on a small VPS. Keep password security parameters unchanged unless separately justified.
4. Optimise invoice eligibility and dashboard totals: avoid loading the entire backlog for each page visit; move filtering/aggregation/pagination into tenant-scoped SQL or maintain appropriate summaries with correct invalidation. Inspect query plans and indexes with realistic tenant histories before adding a cache.
5. Use the planned worker queues for costly PDF preparation and other background work, with separate concurrency budgets. Measure PDF rendering and populated invoice/stock workflows independently.
6. Run the same tests on the actual production-sized server, through the proxy. Define the expected interaction rate for 1,000 accounts, then require zero unexpected errors, an agreed p95 target (for example <1 second for routine API calls), spare capacity, and a longer soak. If one dashboard visit/user/30 s is the target, prove at least 33 complete pages/s and preferably about 67/s for double the headroom, including all underlying requests. Repeat with large tenants, simultaneous logins and slow dependencies. Complete the existing deployment, backup and restore requirements before production data.

## Reproduction

From the repository root:

```powershell
docker build -t bp-load-backend:local ./backend
docker build -t bp-load-frontend:local ./frontend
docker build -f backend/tools/Dockerfile.loadtest -t bp-load-client:local backend/tools
Set-Location backend
uv run python tools/loadtest.py --linux-client --output ../docs/loadtest-results.json --duration 15
uv run python tools/loadtest.py --linux-client --admission --diagnostic --output ../docs/loadtest-admission-results.json --duration 15
uv run python tools/loadtest.py --linux-client --workers 4 --admission --comparison --output ../docs/loadtest-four-workers-results.json --duration 15
```

For the PDF benchmark, from the repository root, mount the absolute `backend/tools/pdf_benchmark.py` path into the backend image and use an inert configuration (no database connection is permitted):

```powershell
$pdfProbe = (Resolve-Path backend/tools/pdf_benchmark.py).Path
docker run --rm -e APP_ENV=development -e AUTH_MODE=disabled -e DATABASE_URL=postgresql+psycopg://unused:unused@127.0.0.1:1/pdf_only_test --mount "type=bind,source=$pdfProbe,target=/probe.py,readonly" bp-load-backend:local python /probe.py
```

`TEST_DATABASE_URL` must refer to the dedicated local test server on localhost:5433. No credentials or fixture tokens are written into reports. Raw aggregate results are in the adjacent JSON files. Throughput divides successes by elapsed time including draining outstanding requests; error rates and latency percentiles are more useful for the paced phases. The initial paced diagnostics also included an extra final generator sleep; the later comparison corrects that sleep.

The HTTP generator itself reached approximately one CPU core at high concurrency in some admission experiments and in the lightweight health control. Treat saturated-generator stages as lower bounds on throughput, not the app's absolute capacity ceiling. The original pool-starvation failures occur with the generator well below saturation.

The initial JSON reports' `backend_error_counts` examined container stdout only, so an empty counter does not imply that no stderr exception occurred. HTTP statuses, latency, PostgreSQL diagnostics and directly observed checkout exceptions establish the failure above. The saved harness now also examines stderr for those aggregate exception counters.
