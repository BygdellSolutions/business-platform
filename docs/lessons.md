# Lessons

Rules learned from corrections by the project owner. Review at session start; add an entry after every correction.

- **"Organization" always means the tenant.** A customer that is a business is a `company` (customer type `person` | `company`).
- **Module fields are normal domain attributes; UDFs extend, they do not replace.** Stable attributes of a domain entity (a horse's `birth_year`, `sex`, `breed`) are real, validated columns in that module, not UDFs. UDFs add organization-specific fields on top of the normal model.
- **A transaction's lifecycle status is not its invoicing state.** `draft` / `completed` / `cancelled` describe the transaction only; `completed` means finalized and ready for future invoicing, not "uninvoiced". Invoice state will be its own relationship, not another lifecycle status.
- **Totals and VAT breakdowns sum the stored line amounts.** Never recompute grouped VAT from grouped net totals; per-line half-up rounding is the single rounding rule.
- **Keep the header minimal.** The Transaction header has no note or other free text until a real need appears.
- **Boundary tests enforce imports and registrations, not vocabulary.** Generic code and docs may use ordinary domain words. What must hold is who imports whom: core, generic capabilities and modules meet only through the core registry.
- **Required custom fields participate in finalizing a record, without Sales importing Custom Fields.** Core exposes a generic lifecycle-validation seam: capabilities register validators and modules call the seam. Failures carry the record type, id, field and label so a client can locate the problem.
- **`show_on_invoice` means "eligible to be snapshotted".** Invoices store the rendered label and value at issuance and never resolve live custom-field or reference data for an existing invoice.
- **Role checks live in core, not in feature modules.** Use `require_role` / `roles_required`; the role is always the one in the active membership.
- **Automated tests never touch the development database.** pytest and Playwright use a separate PostgreSQL server (`postgres-test`) via `TEST_DATABASE_URL`, rebuilt from migrations. A guard refuses anything not named `*_test` or hosted on the development server, and there is no fallback to the development database.
- **Enforce the money rule where money lives, not as a global ban.** Decimals are strings via branded types, scoped lint rules in the money-handling folders and tests; `parseFloat`, `Number` and `Math` stay available elsewhere.
- **The frontend never copies backend limits.** Digit counts, ranges (0 to 100, greater than zero), precision and uniqueness are the backend's rules. The frontend checks only that a typed value has the right shape and shows the backend's 422 on the field; a copied limit would drift from the backend.
- **A mutation must also refresh the router, or Back shows stale lists.** Next.js reuses cached pages on browser Back/Forward. After a create, `router.push()` is followed by `router.refresh()`; after an edit or a status change, `router.refresh()`. This was found by a browser test (Back to a list visited before a create did not show the new record), so keep that test.
- **End-to-end specs share one database, so a spec never depends on what other specs created.** Look records up by a unique name; never rely on "the first N rows" (the dashboard preview) or on a name being absent from a capped list. Fixtures that must appear in a capped list get a leading `000` so they sort first.
- **A picker selects by id, never by text, and an unchanged reference is never re-sent.** Two customers can have the same name, and a customer can become inactive after being assigned. The picker holds `{id, label}`, displays the current selection even if it is no longer offered, and submits only the id; an edit sends a relationship only when the user changed it, which matches the backend (it checks only new targets).
- **A keyboard test needs a real form.** In jsdom, Enter does not submit a form that has no submit button, so a test of "Enter must not submit" passed even with the guard removed. Give such test forms a submit button, and confirm with fault injection that the test fails without the guard.
- **Stale edits are refused by the server, not detected by the screen.** A tab cannot know it is stale. Anything a person edits in a browser carries the version it is based on, and the server compares it under its row lock before changing anything. Use a counter, not `updated_at` (ties; a parent does not change when a child does), and give the token the granularity of what is edited (header vs lines vs the whole document).
- **A conflict must never destroy what the user typed.** After a stale refusal keep the draft, switch Save off, show what is on the server now, and let the user choose; loading the latest around an open editor is fine because it does not touch the editor's own state. Throwing the draft away is the user's choice, not the default.
- **A mutation test that has no effect on the page proves nothing.** Mocking `router.refresh` as an instant call hides the pending state of the real router (it suspends until the new page arrives). The test harness models that with a gate, and the UI dims what is about to change.
- **A single-flight guard needs a same-instant test.** Disabled buttons cover the user who clicks twice; only a test that fires two clicks inside one act proves the guard itself.
- **Equivalent mutants are reported, not hidden.** When a fault cannot be observed because another guard makes it unreachable (judging a save by the newest version when Save is already off for a newer one), say so instead of counting it as covered.
- **Genericity is enforced by a test, not by intention.** A generic layer gets a boundary test: imports limited to generic layers, no comparison of metadata to literals, no domain words in code or comments (and the check is tested against bad samples). Without it, the first "just for this field" special case arrives quietly.
- **Read what the backend enforces on write before designing the form.** The Custom Fields API checks every required field and every dependency against the FINAL state of a record on each write, so the UI saves a record's fields together (only the changed ones) and sends a parent change and its cleared children in one request. Field-by-field autosave would have been refused.
- **Answers belong to the question that was asked, including the function that asked it.** A picker whose choices depend on another field must treat a changed search function as a new question; otherwise the old parent's choices stay visible until the new answer arrives.
- **Closing or clearing a control must not pop something over the next control.** Returning focus to a picker after "Clear" re-opened its list on top of the Save button; found only because a browser test clicked Save. Restore focus without triggering open behavior.
- **Keep the label text clean.** A visible `*` inside a `<label>` changes the label's text for tests and for tools that match it; draw the marker with CSS and express the meaning with `aria-required`.
- **Organization context belongs in the URL.** A shared cookie would let one tab silently re-target another tab's writes; the BFF takes the organization from the URL and FastAPI verifies membership.
- **Compare `Origin` with the `Host` header, and redirect with a relative `Location`.** Next may normalize the request URL host (for example `localhost` for `127.0.0.1`), which would reject legitimate same-origin requests or move the browser to a host without its cookie.
- **Never assume data the platform does not know.** A currency (or any financial attribute) is configured explicitly; a migration must not backfill an assumed value into existing records, even a likely one. Keep the column nullable, show "not recorded", and offer an explicit, confirmed action for the owner to state it. Prove it with a migration test on data that has no value.
- **Do not promise guarantees you do not control.** The invoice counter rolls back with the issuing transaction and issued numbers are never reused, but that is not "gapless numbering" as a business guarantee: whether a jurisdiction requires it is policy, so neither the docs nor the schema claim it. Say what the mechanism does, not what a regulation might want.
- **Database triggers protect a module's own tables; cross-module rules live in the core seam.** An immutability trigger on invoice tables is fine. A trigger that makes the Sales lifecycle depend on Invoicing tables is not: Sales would silently depend on another module. The veto goes through the lifecycle seam as a registered validator, protected by locking tests.
- **Do not model speculative features.** No one-value enum (`document_type = 'invoice'`) for credit notes that are not designed, and no uniqueness constraint (`number_text`) that is really formatting policy. Add the column or constraint with the feature that needs it.
- **A change that must not race a creation takes the same row.** The currency check and the creation of prices serialize on the organization row (`FOR SHARE` for creators, `FOR UPDATE` for the change); otherwise "refuse once prices exist" has a window. Prove each ordering with real, separate connections and a request that is still waiting while the other side is uncommitted.
- **A composite foreign key with a nullable column is not enforced for NULLs (MATCH SIMPLE).** `(organization_id, id, billing_customer_id, currency)` only protects a row whose own `currency` is NOT NULL. Make the referencing column NOT NULL, or the "same currency" rule silently does not apply.
- **When a test must undo a database rule, do it inside the rolled-back test transaction.** PostgreSQL DDL is transactional: `ALTER TABLE … DISABLE TRIGGER` inside the test's transaction recreates a pre-feature row and disappears with the rollback.
