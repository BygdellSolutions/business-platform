# Changelog

All notable changes to `business-platform` will be documented in this file.

## [Unreleased]

### Added
- **Invoicing backend** (no frontend or PDF yet; `docs/architecture.md`, "Invoicing as built"). An invoice is built from one or more whole **completed** transactions of the same billing customer and the same non-NULL currency that are on no other draft or issued invoice. `POST /api/invoices` locks the sources in id order and copies the stored Sales lines verbatim, the totals and VAT breakdown (stored sums of the stored line amounts), versioned customer and issuer snapshots and the custom fields flagged `show_on_invoice` (generically). `PATCH` edits a draft's dates and description, `POST /{id}/issue` re-verifies the reserved sources and amounts (`409 source_changed` otherwise), re-takes the party and custom-field snapshots, allocates the number and freezes the invoice, `DELETE` removes a draft and releases its transactions. `GET /api/invoices`, `GET /api/invoices/{id}`, `GET /api/invoiceable-transactions` and `GET /api/invoices/by-transaction`. `If-Match` versions as in Sales; every member reads, owner/admin/accountant mutate.
- Tables `invoices`, `invoice_transactions`, `invoice_lines`, `invoice_vat_rows`, `invoice_counters` with tenant-safe composite references; `UNIQUE (organization_id, transaction_id)` is the final duplicate guard (its race failure is translated to the ordinary `already_invoiced` 409); `UNIQUE (organization_id, series, number)` is the only numbering uniqueness (`number_text` is a stored label, not unique); invoice and source currency are NOT NULL, so a currency-less transaction can never be linked; no `document_type`. Migration `f74d0b3c9e56` is additive (it adds one unique key to `transactions` and changes no existing row).
- Numbering from `invoice_counters`, allocated last at issuance in the same transaction (atomic upsert, no `MAX()+1`); a failed issuance rolls the allocation back, an issued number is never reused, drafts have none. Documented as a mechanism, not a legal "gapless numbering" guarantee.
- A transaction on a draft or issued invoice cannot be reopened or cancelled: Invoicing registers a validator on the core lifecycle seam (Sales imports nothing from Invoicing; no trigger on a Sales table involves invoicing).
- Invoice-local PostgreSQL triggers make an issued invoice and its documents immutable (update, delete, inserting children) and restrict a draft to its header data and snapshot content.
- `position` and `definition_id` on custom-field value reads, so a consumer that keeps a copy takes it from one consistent read.
- Tests: draft creation contract (what may combine, derived fields, exact copies, VAT breakdown parity with Sales, snapshots, roles, foreign/random ids, isolation), lifecycle (If-Match, issue, numbering, reservation, failures leave no trace, drift detected at issuance), raw-SQL database guarantees (immutability, CHECKs, composite keys, no Sales trigger involves invoicing), historical read independence (live changes and deletions do not change an issued invoice; an SQL recorder proves a read touches only invoicing tables), committed-data concurrency (simultaneous creators, creation racing reopen/cancel in both orders, Sales line/custom-field writes, snapshot races never torn, N concurrent issuances give 1..N, a failed issuance's number is reused by a waiter, issue/delete and issue/edit races), a migration test on existing data, and the amended module boundaries (Invoicing may use only named submodules of Sales and Custom Fields; the reverse is forbidden).
- **Invoicing prerequisites** (the Invoice tables themselves are NOT built yet).
- **Organization settings.** Organizations gain `legal_name`, an optional business profile (address line 1 and 2, postal code, city, country code, registration number, VAT number) and `default_currency`. `GET /api/organization` for any member, `PATCH /api/organization` for owner and admin only; the organization is always the active one (no id anywhere), updates are partial with `extra="forbid"`, blank means "not set". A settings page (`/o/{orgId}/settings`, in the nav) gives owners/admins the form and every other role the same values read-only.
- **Customer billing profile.** Customers gain the same seven optional free-text fields (nullable, blank stored as NULL). Only the shape of the country code is checked (two capital letters; lower case is upper-cased) by the schema and a CHECK; no jurisdiction-specific validation. The customer API and form carry them.
- **Currency foundation.** The default currency is explicitly configured per organization and never assumed. Each transaction snapshots it at creation (`transactions.currency`, never accepted from a client) and a database trigger refuses any later change; an organization without a currency cannot create transactions (`409 currency_not_configured`). Transactions that predate currencies keep no currency: `GET /api/transactions/currency-status` and the explicit owner/admin action `POST /api/transactions/assign-currency` (and a confirmed button on the settings page) are the only way to give them one. Changing the default currency is refused once items or transactions exist (`409 currency_locked`), documented as a temporary rule. Creating a transaction/item and changing the currency serialize on the organization row (`FOR SHARE` / `FOR UPDATE`).
- **Core lifecycle seam** now has `reopen` and `cancel` events next to `complete`; Sales asks the seam for all three (after the state and `If-Match` checks, under the row lock). No validator vetoes reopen/cancel yet. Core also gained currency guards on the registry (`add_currency_guard`), which Sales uses.
- **Generic custom-field flag filter** (`?flag=required|show_in_form|show_in_table|show_on_invoice`) on definitions and values, so the fields eligible for a future invoice can be retrieved without any invoice-specific dependency in Custom Fields.
- `UNIQUE (organization_id, id, transaction_id)` on `transaction_lines` (the target of the future invoice-line foreign key).

Both are additive and **do not backfill**: existing organizations and transactions keep NULL, which a migration test proves on a database that holds currency-less data (it also covers downgrade, re-upgrade and `alembic check`).

- **Optimistic concurrency for Sales.** Transactions and lines carry an integer `version` (and transactions a `header_version`, so a header edit is not blocked by a line changed elsewhere). Documented in `app/modules/sales/versioning.py` and the README, including why a header (not a body field) and why `409` (not `412`).

### Security
- Issued invoices are immutable at the database level (triggers) as well as in the application; their sources are protected from deletion by tenant-safe RESTRICT references; invoice creation takes row locks on the source transactions in a fixed order and verifies everything under them.
- Organization settings can be changed only by owners and admins, enforced by the server (the UI only hides the form); the organization is never taken from the request, so a change can only reach the caller's own organization, and a foreign organization id is the same 404 as a random one.
- A transaction's currency cannot be changed once set, even by raw SQL (trigger), and the migration does not assign a currency to existing financial data, so no stored price is silently reinterpreted.
- The default currency cannot be changed while items or transactions exist; the check and the creation of prices serialize on the organization row, so a concurrent creation cannot slip past it.
- The browser never calls FastAPI and never sends identity or organization headers: the BFF builds backend requests from scratch, validates only shapes (UUID, known API areas, safe path segments, same origin, JSON bodies) and leaves membership decisions to FastAPI, which answers 404 for organizations the user does not belong to.
- Tenant-owned records can no longer have their `organization_id` changed after creation (ORM guard); Customer, Item and Horse requests containing `organization_id` are rejected. Cross-tenant references from horses to customers are rejected by both the API and PostgreSQL composite foreign keys.
